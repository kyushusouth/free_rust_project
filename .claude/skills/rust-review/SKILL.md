## 手順

1. `docs` 配下を対象にドキュメントを読み取る。DesignDoc やテスト計画が格納されている。
2. コードを読みとる。引数にパスが指定された場合はそのファイルのみを、そうでない場合は `src` および `tests` 配下を対象にする。
3. 後述する「レビュー観点」に沿ってコードをレビューする。
4. 各返答項目に「プレフィックス一覧」から適切なプリフィックスを選んで付与し、結果を報告する。

## レビュー観点

### 設計

| 観点 | 確認ポイント |
| --- | --- |
| アーキテクチャ | 選定しているフレームワークに適したアーキテクチャになっているか。 |
| 責務設計 | 構造体や関数の責務が分離されているか。 |
| 変更容易性 | 変更しやすい設計になっているか。 |

### 理解容易性

| 観点 | 確認ポイント |
| --- | --- |
| 簡潔性 | 条件分岐やネストが深すぎず、ロジックが簡潔で明確か。 |
| 可読性 | 読みやすいコードか。ロジックを追いやすくなっているか。 |
| 冗長性 | ロジックが重複していないか。 |
| 一貫性 | コードやコメントの書き方、コメントの口調に一貫性があるか。 |

### 命名

| 観点 | 確認ポイント |
| --- | --- |
| タイポ | スペルや英文法に誤りがないか。 |
| 責務・役割の明確性 | 構造体の名前や、そのフィールド名、メソッド名から責務が直感的に伝わるか。関数名から、関数の目的や処理内容が直感的に伝わるか。変数名から、変数が保持するデータやプログラムにおける用途が直感的に伝わるか。十分意味が狭く、かつ冗長でない名前になっているか。 |

### コードスタイル

| 観点 | 確認ポイント |
| --- | --- |
| 静的解析違反 | 静的解析ツールで検証される問題がないか。 |
| アクセス修飾子の適切さ | モジュールを必要な範囲からだけ使えるように公開しているか。 |

### 機能・性能

| 観点 | 確認ポイント |
| --- | --- |
| 機能要件 | 期待の挙動と異なっていないか。 |

### テスト

| 観点 | 確認ポイント |
| --- | --- |
| テスト容易性 | テストコードを書きやすい設計になっているか。 |
| テストケース | 境界値を抜け漏れなく検証しているか。正常系と異常系を網羅できているか。副作用を伴う処理のテストも適切に実装されているか。 |

### ドキュメント

| 観点 | 確認ポイント |
| --- | --- |
| 整合性 | コードとドキュメントの内容に整合性があるか。 |
| 内容の適切さ | 設計意図を書いているか。具体的な処理内容を読む負担がかかりすぎないくらいの粒度で書いているか。 |

## プレフィックス一覧

| プレフィックス | 意味 |
| --- | --- |
| must | 必ず修正してほしい |
| want | 修正してほしい |
| imo | 個人的には修正した方が良さそうに思う |
| nits | 些細な指摘 |
| ask | 単純に質問 |
